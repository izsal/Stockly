# Stockly — Database Design

- Database: Neon PostgreSQL
- ORM: Drizzle ORM
- Status: MVP schema specification

## 1. Design principles

1. PostgreSQL is the source of truth.
2. Business tables are tenant-scoped with `workspace_id`.
3. Use UUID primary keys for business entities; retain Better Auth's required text IDs for authentication records and user references.
4. Store timestamps as `timestamptz`.
5. Store currency values as integer minor units (for IDR, whole rupiah) or PostgreSQL `numeric`; do not use floating point.
6. Store current stock in `inventory_stocks` for fast reads.
7. Store every stock change in immutable `inventory_movements`.
8. Update stock balance and movement ledger atomically.
9. Use soft deletion for products with movement history.
10. Enforce workspace-scoped uniqueness.

## 3. Tables

### 3.1 workspaces
- `id` UUID primary key
- `name` varchar(120), required
- `slug` varchar(80), required
- `created_at`, `updated_at` timestamptz
- Unique index on `slug` (global workspace URL identifier)

### 3.2 memberships
- `id` UUID primary key
- `workspace_id` UUID FK
- `user_id` FK to Better Auth user
- `role` enum: `OWNER`, `STAFF`
- `created_at` timestamptz
- Unique `(workspace_id, user_id)`
- Index `(user_id, workspace_id)`

A workspace should have exactly one initial owner. Ownership transfer is out of MVP scope.

### 3.3 categories
- `id` UUID primary key
- `workspace_id` UUID FK
- `name` varchar(100), required
- `description` text, nullable
- `created_at`, `updated_at`
- Unique `(workspace_id, name)`

### 3.4 suppliers
- `id` UUID primary key
- `workspace_id` UUID FK
- `name` varchar(160), required
- `phone` varchar(40), nullable
- `email` varchar(255), nullable
- `address` text, nullable
- `notes` text, nullable
- `created_at`, `updated_at`
- `deleted_at` nullable

### 3.5 warehouses
- `id` UUID primary key
- `workspace_id` UUID FK
- `name` varchar(120), required
- `code` varchar(40), nullable
- `address` text, nullable
- `is_default` boolean, default false
- `created_at`, `updated_at`
- Unique `(workspace_id, code)` when code is not null
- MVP: create one default warehouse automatically per workspace; UI for additional warehouses deferred.

### 3.6 products
- `id` UUID primary key
- `workspace_id` UUID FK
- `category_id` UUID nullable FK
- `name` varchar(180), required
- `sku` varchar(80), required
- `barcode` varchar(100), nullable
- `description` text, nullable
- `unit` varchar(30), required, default `pcs`
- `cost_price` numeric(14,2), required, default 0
- `selling_price` numeric(14,2), required, default 0
- `minimum_stock` integer, required, default 0
- `is_active` boolean, default true
- `created_at`, `updated_at`
- `deleted_at` nullable
- Unique `(workspace_id, sku)`
- Partial unique `(workspace_id, barcode)` where barcode is not null
- Index `(workspace_id, name)`
- Index `(workspace_id, category_id)`
- Check prices >= 0 and minimum_stock >= 0

SKU uniqueness should be case-insensitive if the product requirements choose case-insensitive SKU. Normalize SKU to uppercase before saving and querying.

### 3.7 inventory_stocks
- `id` UUID primary key
- `workspace_id` UUID FK
- `product_id` UUID FK
- `warehouse_id` UUID FK
- `quantity` integer, required, default 0
- `updated_at` timestamptz
- Unique `(workspace_id, product_id, warehouse_id)`
- Check `quantity >= 0`
- Index `(workspace_id, warehouse_id)`

### 3.8 inventory_movements
- `id` UUID primary key
- `workspace_id` UUID FK
- `product_id` UUID FK
- `warehouse_id` UUID FK
- `supplier_id` UUID nullable FK
- `created_by` FK to Better Auth user
- `type` enum: `IN`, `OUT`, `ADJUSTMENT`
- `quantity_delta` integer; signed (+/-)
- `quantity_before` integer
- `quantity_after` integer
- `reason` varchar(80), nullable (e.g. PURCHASE, SALE, DAMAGE, CORRECTION)
- `reference_number` varchar(100), nullable
- `notes` text, nullable
- `created_at` timestamptz
- Check `quantity_after = quantity_before + quantity_delta`
- Check before/after are >= 0
- Index `(workspace_id, created_at desc)`
- Index `(workspace_id, product_id, created_at desc)`
- Index `(workspace_id, warehouse_id, created_at desc)`

Movement rows are append-only. Corrections should be represented by a new adjustment movement, not by editing/deleting a prior movement.

## 4. Relationships and tenant integrity

Every business table includes `workspace_id`. Every service query must filter by the authenticated workspace.

Where practical, enforce composite references such as:
- `(workspace_id, product_id)` references a unique key on `products(workspace_id, id)`.
- `(workspace_id, warehouse_id)` references `warehouses(workspace_id, id)`.
- `(workspace_id, supplier_id)` references `suppliers(workspace_id, id)`.

This prevents a record from one workspace being attached to another workspace's product, warehouse, or supplier. If composite foreign keys are not implemented in the first migration, application-level checks and tenant-isolation tests are mandatory, and the database constraints should be added before production scale.

## 5. Stock movement invariants

For each `(workspace_id, product_id, warehouse_id)`:
- A stock row exists with quantity 0 when the product is first assigned to the default warehouse.
- Opening stock is recorded as an `IN` movement with reason `OPENING_BALANCE`; do not silently seed a non-zero balance.
- `quantity_delta` is signed.
- `quantity_before + quantity_delta = quantity_after`.
- `inventory_stocks.quantity` equals the latest ledger balance.
- All updates happen in one transaction.
- A stock-out is rejected if the resulting balance would be negative.
- Lock the stock row or use a safe atomic conditional update to prevent race conditions.

## 7. Recommended indexes

At minimum:
- `memberships(user_id, workspace_id)`
- `products(workspace_id, sku)` unique
- `products(workspace_id, barcode)` unique where barcode is not null
- `products(workspace_id, name)`
- `inventory_stocks(workspace_id, product_id, warehouse_id)` unique
- `inventory_movements(workspace_id, created_at desc)`
- `inventory_movements(workspace_id, product_id, created_at desc)`

## 8. Migration and seed strategy

- Use Drizzle Kit to generate and commit migration files.
- In this v0 workspace, apply DDL through the Neon migration integration; do not run Drizzle Kit migrations directly against the connected database.
- Never edit a migration that has already been applied to a shared/production database; create a new migration.
- Keep demo seeding out of the foundation milestone; seed only a dedicated development branch when later feature work requires fixtures.
- Do not use production customer data in development.
- Use a separate Neon branch/database for development if available within the chosen plan and quota.
